The inventory uses official release metadata, pinned source feature modules/screens and feature settings. Source presence is evidence for a capability to assess, **not proof that it is enabled, stable or available on both upstream platforms**. No device-based upstream acceptance audit has been performed. Do not include later prereleases in the stable comparison silently. The Android v26.09.3 prerelease is outside this baseline.

[Android feature flags](https://github.com/element-hq/element-x-android/blob/477c81399761c02db99f3ae9447a528f3be4d1d7/libraries/featureflag/api/src/main/kotlin/io/element/android/libraries/featureflag/api/FeatureFlags.kt) explicitly disable threads, multi-account, QR login, message search, slash commands and several unread behaviors by default in this snapshot; knock and gallery sending are Labs features. [iOS settings](https://github.com/element-hq/element-x-ios/blob/47f881c5077c5a924abe4805b34097a1a2902a34/ElementX/Sources/Application/Settings/AppSettings.swift) and release notes must be checked independently. Native iOS calls are marked in development in this release. Fern's multi-account requirement is a product requirement regardless of upstream defaults.

Aurora is an experimental SDK integration reference, not a released web/desktop parity standard. Frappe UI and Cinny guide Fern's interface; upstream Element chrome is not a design requirement.

## Platform support policy

These are target qualification lanes, not claims that every browser already works. Record exact browser/OS versions in CI and device reports; qualify current and previous stable releases at each release cut rather than promising untested minimums.

| Platform | Current evidence | Qualification target / issue |
| --- | --- | --- |
| Chromium desktop | Automated desktop, WASM builder and production shell checks | Current + previous stable on Linux/macOS/Windows; live accounts and calls, #4 / #31 |
| Android Chromium/PWA | Chromium 390px viewport only; no real Android-device proof | Current + previous stable; physical midrange Android and low-memory profile, #9 / #31 |
| Firefox desktop | Unverified | Current + previous stable; IndexedDB/WASM, E2EE and calls, #31 |
| Safari macOS | Unverified | Current + previous stable; storage lifecycle and media permissions, #31 |
| Safari iOS / installed PWA | Unverified | Current + previous stable iOS on real devices; suspension, storage eviction and install, #31 |
| Native desktop | No package | Windows/macOS/Linux targets and minimums chosen by architecture proof, #28 / #29 |
| Native Android / iOS | No package | Minimum OS/device support chosen after SDK and background prototypes, #28 / #30 |

Unsupported browser capabilities must produce an actionable UI state. Browser background ringing/push depends on platform support and infrastructure; PWA installation does not establish native background parity. Native minimums remain deliberately unset until prototype evidence exists.

## Homeserver and deployment prerequisites

- Current login requires password authentication; current client uses native sliding sync. Validate discovery/version negotiation and give useful unsupported-server errors (#4, #8). OIDC-only and SSO-only servers are not currently supported (#11, #12).
- E2EE, recovery, media, directory, moderation and push capabilities must be exercised against real homeservers. Test at least one pinned fixture and one independently operated compatible server before production qualification; record exact versions and server settings.
- Calls require working MatrixRTC/LiveKit infrastructure and a compatible Element Call host. Static Pages hosting alone provides neither call infrastructure nor a push gateway (#24, #25).
- GitHub project Pages is supported for the public app shell and repository subpaths. Its shared origin is not a separate security boundary from other projects on the same account. Use a dedicated trusted HTTPS origin for sensitive accounts; see the current session-storage limitations in [README](../README.md#local-data), addressed by #7.
- Authenticated media, decrypted events and credentials must never enter public shell caches. Local storage cleanup, quota failures, SDK schema upgrades and service-worker updates are release concerns (#7, #31).

## Scope boundaries and refresh procedure

Element Pro/enterprise policy, managed content-scanner backends, Element-specific telemetry providers, migration from Element Classic's private local stores and Element-branded distribution services are not implicit Fern requirements. Portable account/session recovery, privacy-preserving diagnostics and user safety are required. If an enterprise or migration feature becomes required, open a scoped issue and record the platform/protocol boundary here.

Experiments are tracked separately from stable defaults (#16, #19 and the experimental-capability issue). A failed or unavailable SDK experiment needs a documented follow-up, not an unsupported parity claim. Features unrelated to the pinned inventory (for example bridges or arbitrary bots) need their own product scope.

For a refresh: pin new **stable** tags and source SHAs; inspect release notes, screens/modules and flags on both platforms; update rows and issue links; add newly found gaps to #2 and their milestones; rerun the qualification matrix. Do not silently compare against moving `develop` branches. This audit is a source-based planning baseline; #35 owns hands-on upstream comparison and complete product sign-off.
