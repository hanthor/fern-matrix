# Architecture

`src/sdk/engine.ts` is the only app-specific adapter to the vendored Rust SDK. The SDK initializes lazily when real accounts are restored or added. Its Rust-backed clients, task handles, timelines, event identifiers and media sources are kept outside Vue reactivity. `src/store.ts` owns normalized render data and the explicitly separate demo mode.

Each login gets a UUID store and a random IndexedDB passphrase. Sessions are keyed by store UUID rather than user ID, so two sessions for the same Matrix user remain distinct. Each account has its own sync service and observer handles. Room selection uses a generation counter to ignore delayed results from a previously selected account or room. The draft key includes both account and room IDs.

Room list observation triggers summary refreshes. Refreshes use batches of 20 SDK reads and are coalesced per account. A four-second refresh also keeps summaries current when SDK callbacks are sparse, with exponential backoff to a one-minute cap while it keeps failing. Active rooms are subscribed through the room list service. The SDK retries internally without flipping its sync-service state, so the engine probes the public versions endpoint on each tick: three consecutive probe failures flip the account offline with a single error (auth failures keep the expiry path and never flip), and Retry connection re-probes immediately. Watch stops cancel timeline/typing listeners and drop that watch's native timeline object (identity-guarded, so a stale stop cannot evict a newer watch). Sends to rooms this client created encrypted wait (bounded 30s) for the SDK to confirm the encryption state before the first send, so a syncing client can never emit a plaintext opener; rooms with any other origin are untouched. Restored sessions re-check native sliding-sync support and surface a clear error instead of starting a dead sync.

The call iframe is connected to `makeWidgetDriver`; inbound messages require an exact origin, iframe window, and widget ID match. SDK Element Call permissions constrain access to the room and current user/device. The iframe does not receive the account access token in its URL. The bridge is canceled and listeners removed when the call view closes.

The demo is persisted separately. User-uploaded demo blobs are not persisted across reloads because their object URLs would expire. Recovery keys and passwords are not written to the draft store. The tour loads only on the dedicated demo instance (GitHub Pages builds with `VITE_FERN_DEMO=1`) or an explicit `?demo=1` override (`?demo=0` forces the gate anywhere); every other build starts empty at a login gate prompting sign-in or account creation, with an in-app "Explore the demo" escape hatch. Unit tests always load the fixtures; run browser tests against a demo-enabled dev server (`VITE_FERN_DEMO=1 npm run dev`, which CI configures via the Playwright webServer env) or the specs will land on the gate. On demo builds the first real sign-in retires the demo account (its last snapshot is kept for a reseed); the demo returns only when the last real account leaves the device.

## Validation

- `npm test`: batched SDK timeline updates, local-echo replacement, history ordering and vector reset/removal behavior; verification timeout-signal mapping and state cleanup; failed-send retry/discard handle mapping; watch-stop timeline eviction with stale-stop guard; offline flip/recovery counting, auth-failure exemption, backoff bounds and retry re-probe.
- `npm run test:e2e`: desktop messaging, replies, edits, reaction toggling, poll voting and reload persistence; account and draft isolation; creation and quick switching; security view; phone navigation and width; bounded long-timeline rendering under CPU throttling; actual Rust WASM initialization and client creation with encrypted IndexedDB against a mocked versions endpoint.
- `npm run test:integration`: real pinned Synapse and two isolated Rust SDK browser clients; see [live integration setup and evidence boundaries](INTEGRATION.md).
- `npm run build`: TypeScript / Vue checking, static build, versioned offline shell and base-aware manifest generation.
- Production smoke check: Pages subdirectory asset resolution, SDK WASM initialization, shell offline reload and dark / mobile rendering.

Browser tests default to Playwright's installed Chromium (`npx playwright install chromium`). Supply `FERN_CHROMIUM_PATH=/path/to/chromium` to use another installation. The separate integration workflow exercises browser and real-server tests in CI.

Live Matrix tests require dedicated test accounts. Verify password login and reload restoration, independent sync with two accounts, encrypted messages / replies / edits / reactions and attachments between clients, history recovery, emoji verification, invites / DMs / directory membership, interrupted network recovery, logout, and a call with a second participant. The disposable suite now verifies the core unencrypted adapter scenarios and session isolation. Independent E2EE, recovery/verification, interrupted-network, federation and call scenarios remain unverified. Calls require a homeserver advertising MatrixRTC and functioning MatrixRTC authorization / LiveKit services.

## Performance

Timelines render a bounded window (currently the latest 150 messages, expandable in 200s) instead of mounting every loaded message; pagination, scroll anchors and the loaded-message search operate on the full loaded set. Explicit event navigation expands the window to cover its target, so permalinks and jump-to-message work for older messages too. The timeline uses the feed pattern (`role="feed"` with per-row position/setsize) so screen readers keep the full-list position of windowed rows. The regression gates are `long timelines render a bounded window within budget` and `event focus reaches messages older than the render window` in `tests/browser/client.spec.ts`, plus `startup, memory and scrolling stay within budget` in `tests/browser/perf.spec.ts`: 2000 loaded messages render at most ~170 rows; cold start under 30s, cached start under 8s, account switch under 3s, heap under 300MB, scrolling above 5fps, all under 4x CPU throttling, the agreed stand-in for a low-end mobile profile (no device lab is available, so treat phone numbers as approximate). Measured on this box: 2-17s cold (dev-server transform noise), ~1.5s cached, ~0.2s switch, 150 rows, 65-100MB heap, ~2.5s WASM compile plus platform init, 9-59fps scrolling. Re-measure with `npx playwright test tests/browser/perf.spec.ts`; the run logs every observed number. The SDK stays on the main thread: its UniFFI bindings initialize platform state there and loaded WASM is cached after first use, so worker offload is future work, not a justified change now; delivery constraints (host compression and the WASM MIME type) are documented under Deployment/hosting notes.

Artifact delivery: the SDK WASM is ~50.7 MB uncompressed (~11.8 MB with gzip -9) and loads only when a real account needs it. GitHub Pages does not guarantee compression or `application/wasm` tuning per file, so serve production origins with compression and the WASM MIME type; see README hosting notes. Cold start, cached start, memory and multi-account budgets still need lab measurement.

## Accessibility

The browser suite's `landmarks, names, dialog, touch targets and keyboard flow` test is the automated gate: landmarks, accessible names on all visible controls, exactly one current tab per tab group, dialog semantics with Escape dismissal, a 24px minimum button target on desktop and phone viewports, and an end-to-end keyboard journey (focus composer, type, Enter to send). Measured fixes so far: named the screen-reader-only file input, `aria-current` on selected filter/detail tabs, and 24px minimums for the filters, connect, reaction and image-download buttons.

Manual journeys (no screen-reader lab available; verify with NVDA/VoiceOver before release claims): Tab from the address bar reaches the account rail, room list, timeline history controls, composer and send button in order; Enter sends and Shift+Enter adds a line; Ctrl/⌘+K opens search with autofocus and Esc closes every dialog; emoji/number verification is fully button-operated. Known limits: no focus trap beyond the dialog component's own scope; virtual-keyboard overlap is handled by a `visualViewport` reveal (see `src/a11y.ts`) but still needs a real-device pass.

Reusable patterns: Frappe UI first, custom markup only with a reason. Avatars render through Frappe `Avatar` (`src/components/UserAvatar.vue` keeps pixel sizes and adds image support); unread counts use Frappe `Badge` (green subtle, red solid for mentions); transient notices go through Frappe `toast` with a mounted `ToastProvider` (never a hand-rolled stack); hover hints use Frappe `Tooltip` instead of native `title`; dialog errors use Frappe `Alert`, loading rows use `LoadingIndicator`. Two deliberate exceptions: the rail/nav/main/details landmark skeleton stays custom (Frappe's shells are ERP-oriented, not chat), and space chips plus custom tab groups keep their styling with `aria-current` rather than adopting segmented controls. Caveat: import only what the browser needs — `frappe-ui`'s root index carries an extensionless resource import that Vite resolves but the Node test graph cannot, so `notify()` lazy-loads `toast`. Keep the landmark skeleton's icon-only controls labelled, preserve `prefers-reduced-motion` (global kill-switch in `src/style.css`) and the visible `:focus-visible` outline (with a `forced-colors` override) for any new control.

## Sharing

Outbound sharing only. A message's Share action produces `{ title: 'Fern message', text, url }` where `url` is a `matrix.to` room/event permalink: the platform sheet (`navigator.share`) when present, silent on dismiss, otherwise a clipboard copy of `text + url`. Forwarding is an explicit dialog (source identity, content preview, account-grouped room picker, cross-account warning) that re-sends content as the forwarder — plaintext is decrypted from the source room and re-encrypted for the target, so ciphertext never moves rooms; polls, notices, undecryptable/removed events and unsent echoes are refused. Media forwards as files (voice keeps duration/waveform via the voice transport; images forward as files until the SDK sendImage path works). Inbound `share_target` is deliberately absent from the manifest: receiving shares belongs to the native shell (#29/#30).

## Deployment

The build supports `FERN_BASE_PATH` (must start and end with `/`), default `/`. Vite rewrites app assets, demo attachments use `import.meta.env.BASE_URL`, and `scripts/build-sw.mjs` rewrites the manifest and service worker to that path. Routing uses URL hashes.

## Troubleshooting

If browser tests that `page.evaluate`-import `/src/store.ts` behave impossibly (writes land but the UI never reacts), the long-running `vite` dev server has a corrupted module graph: kill it and let Playwright start a fresh one (`reuseExistingServer` only reuses a listening server).

## Desktop shell

The Tauri 2 shell in `src-tauri/` reuses the same Vite `dist/` bundle (see `docs/NATIVE.md` for the architecture decision). System prerequisites on Debian/Ubuntu: `libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf`. Verified commands from the repo root: `npm run build`, then in `src-tauri/` either `cargo build` (debug binary, needs `icons/icon.png` present for `generate_context!`) or `npx "@tauri-apps/cli@2.12.0" build --debug --bundles deb,appimage` (matches the pinned `cargo install --locked tauri-cli --version 2.12.0` used by `.github/workflows/desktop.yml`, which runs the web gates plus the Linux bundle on every PR and main push). The debug bundle produces `target/debug/bundle/deb/fern-matrix_0.1.0_amd64.deb` and the matching AppImage with desktop entry and icons. The package registers the `fernmatrix://` scheme (`x-scheme-handler/fernmatrix` in the desktop entry): inside the shell the login URL opens in the system browser and the provider returns through the deep link into the existing validated OIDC finish path (`src/tauri.ts`, inert outside Tauri). Signing and the updater run on testing keys (see Releases below); end-to-end provider login through the scheme stays open on #29.

## Releases

Releases are tag-driven: `node scripts/cut-release.mjs <x.y.z>` from `main` verifies `package.json`, `src-tauri/tauri.conf.json` and `src-tauri/Cargo.toml` agree on the version, then creates and pushes `v<x.y.z>`. The tag runs the signed desktop pipeline (deb, AppImage, updater bundle plus `latest.json`, published to the GitHub release by `linux-release`) and the signed Android pipeline (`android-release` builds the APK/AAB, signs post-build with the upload keystore, and attaches both to the same release). All signing keys and CI secrets are testing-grade until rotation; see `docs/NATIVE.md`.

The service worker precaches only the shell and public JS / CSS / fonts / icons. The large Rust WASM is cached when first requested. No Matrix API response, session credential or remote media response enters the app-shell cache. Shell upgrades wait for existing windows to close, avoiding mixed old JS and new WASM artifacts.
